# 快速开始

面向玩家与服主：从零装到一个能跑起来的存档。想搞懂内部原理请看 [工作原理](工作原理.md)。

---

## 一、前置条件

| 组件 | 要求 | 说明 |
| --- | --- | --- |
| Minecraft | **1.18.2 / 1.19.2 / 1.19.4 / 1.20.1 / 1.20.4** | 每个版本有独立构建，装错会被依赖校验拒绝 |
| 加载器 | **Fabric**（Loader ≥ 0.14.0）或 **Forge** | 每个 MC 版本两种各有独立构建；Forge 版 modId 是 `mtr4advanced` |
| Minecraft Transit Railway (MTR) | **4.0.4** | **必须与所选 MC 版本、加载器一致**；所有注入点都是对着 4.0.4 的字节码校验的 |
| Fabric API | 按 MTR 自己的要求装 | **本模组不依赖 Fabric API**，列表里没有它 |
| 安装位置 | **客户端 + 服务端都要装** | 行车计算在服务端，设置界面在客户端 |

> MTR **4.0.5 会让游戏直接拒绝启动** —— `fabric.mod.json` 里写了 `"breaks": { "mtr": ">=4.0.5 <4.0.6" }`。
> 这不是崩溃，是 Fabric 的依赖校验主动拦截，属于有意为之（4.0.5 上注入点不可用）。

## 二、拿到 jar

**方式 A：下载 Release**（如果仓库发了 Release）

按自己的 MC 版本和加载器挑一个：

```
MTR4Advanced-1.0.2-1.18.2Fabric.jar / MTR4Advanced-1.0.2-1.18.2Forge.jar
MTR4Advanced-1.0.2-1.19.2Fabric.jar / MTR4Advanced-1.0.2-1.19.2Forge.jar
MTR4Advanced-1.0.2-1.19.4Fabric.jar / MTR4Advanced-1.0.2-1.19.4Forge.jar
MTR4Advanced-1.0.2-1.20.1Fabric.jar / MTR4Advanced-1.0.2-1.20.1Forge.jar
MTR4Advanced-1.0.2-1.20.4Fabric.jar / MTR4Advanced-1.0.2-1.20.4Forge.jar
```

**方式 B：自己构建**（只需要 JDK 17+，不需要 Gradle、不需要联网）

```bash
cd mtr-train-speed

# 单目标（开发用）：自动在上级目录 / libs 里找 MTR 4.0.4 的 jar
python build.py
python tools/check_targets.py         # 校验注入点，必须 ALL OK

# 全矩阵（发布用）：10 个目标逐个编译 + 逐个校验
#   先把各版本的 MTR jar 放进 _mtr_jars/，命名 MTR-<loader>-4.0.4+<MC>.jar
python build_release.py --jars _mtr_jars --out ../releases
```

预期输出：

```
[1.20.1/fabric] OK  编译 3 轮 / 7 stub  校验 18/18  -> MTR4Advanced-1.0.2-1.20.1Fabric.jar
[1.20.4/forge ] OK  编译 3 轮 / 8 stub  校验 18/18  -> MTR4Advanced-1.0.2-1.20.4Forge.jar
...
成功 10 / 10
```

细节与排错见 [构建与工具](构建与工具.md)。

> **`build.py` 不会自动部署。** 改完代码记得手动把新 jar 拷进 `mods/`，
> 否则游戏里跑的还是旧版本（这是踩过的坑之一）。

## 三、安装

```bash
# 单人 / 客户端（把 <MC版本><加载器> 换成自己的，例如 1.20.1Fabric）
cp ../releases/MTR4Advanced-1.0.2-1.20.1Fabric.jar "<游戏目录>/mods/"

# 服务端（如果开服）—— 用与客户端完全相同的那一份
cp ../releases/MTR4Advanced-1.0.2-1.20.1Fabric.jar "<服务端目录>/mods/"
```

> **装错版本会被拒绝启动**（Fabric 的依赖校验 / Forge 的 mods.toml 版本区间），不会静默出错。

**只装一边会怎样？**

| 装法 | 结果 |
| --- | --- |
| 只有客户端 | 界面能改，但服务端没有这个字段 → 值存不进去。`ReaderBase.unpackValue` 遇到不认识的 key 会跳过，**不会崩、也不会清零** |
| 只有服务端 | 行车按配置文件走（`default-max-speed-kmh` 等），但**客户端没有界面可以改**每条侧线的上限 |

## 四、确认它真的生效了

1. **看日志有没有那行配置生成提示**（首次启动一定会有）：
   ```
   [MTR4 Advanced] 已生成默认配置: <游戏目录>/config/mtr4-advanced.properties
   ```
   找不到这行，说明模组没被加载（或者你翻错日志了）。

2. **开一个侧线的编辑界面**（Siding Screen），最下面应该多出四行控件：

   ```
   列车最高时速 km/h        [    ]
   0 = 不限制，留空同 0
   [ ] 跟随晚点浮动
   [ 复制到车场其他侧线 ]
   ```

   看不到这四行 → 检查是不是装了**两份**本模组（旧 id 的 jar 必须先删掉，见第六节）。

3. **实测一次提速**：把一条侧线的限速设成 40，往前一段设成 120，再在侧线里填「列车最高时速 = 80」。
   列车通过 40 → 120 的分界时，应当**等车尾也越过 40 区段**之后才开始加速，且不会超过 80。

## 五、首次要改的配置

大多数情况下**什么都不用改**。想调的话编辑 `config/mtr4-advanced.properties`：

```properties
tail-controlled-acceleration=true
default-max-speed-kmh=0.0
apply-max-speed-to-time-segments=true
apply-vehicle-length-to-time-segments=true
```

> **改完要重启**游戏 / 服务端才生效（配置只在启动时读一次，没有热重载）。
> **服务端的那一份才是权威** —— 限速与时刻表都只在服务端算。

每个键的含义见 [配置参考](配置参考.md)。

## 六、从旧版（MTR Train Speed）迁移

2026-09-19 改过名：`mtr-train-speed` → `mtr4-advanced`。

| 项 | 旧 | 新 |
| --- | --- | --- |
| mod id | `mtr-train-speed` | `mtr4-advanced` |
| jar 名 | `mtr-train-speed-1.0.0.jar` | `MTR4Advanced-1.0.0.jar` |
| 配置文件 | `config/mtr-train-speed.properties` | `config/mtr4-advanced.properties` |
| mixin 配置 | `mtr-train-speed.mixins.json` | `mtr4-advanced.mixins.json` |

迁移三步：

1. **删掉 `mods/mtr-train-speed-1.0.0.jar`**。
   两个 jar 同时存在会让两份 Mixin 往同一个目标类重复注入 —— 报的错通常很难看出是重复安装导致的。
2. 把新 jar 放进 `mods/`。
3. 旧配置文件里的字段**手工搬**到新文件（文件名变了，模组不会自动读旧的）。
   旧版只有 3 个键，多出来的 `apply-vehicle-length-to-time-segments` 默认 `true`，通常不用动。

Java 包名与 mixin 内部前缀属于纯内部标识，不参与存档与网络序列化 —— **1.0.2 起**已统一为
`cn.nansai.mtr4advanced` 与 `mtr4a$`，升级时无需做任何额外处理。

## 七、卸载

1. 删掉 `mods/MTR4Advanced-1.0.2-<MC版本><加载器>.jar`（**客户端和服务端都要删**）。
2. 侧线里存过的两个字段会留在存档 / 数据库里，但服务端读不到对应 Mixin 时会**直接跳过**这些 key，
   不会报错、不会把值清零。重新装回来时值还在。
3. 配置文件和 `build/` 目录可以留着，也可以删。
4. 如果只是想在服务端临时停用：删掉服务端那份即可 —— 行车计算立刻回到 MTR 原版行为，
   客户端界面还在，但改的值不会落库。
