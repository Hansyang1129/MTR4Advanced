# 构建与工具

本项目的整条工具链是**离线**的：只要一个 JDK，不需要 Gradle、Fabric Loom、也不联网。
这一页说明两个脚本各自做了什么、预期输出长什么样、以及跨平台/换机器时要注意什么。

---

## 一、为什么不用 Gradle

| 常规做法 | 本项目做法 | 理由 |
| --- | --- | --- |
| Gradle + Fabric Loom 拉依赖、重映射、生成 refmap | 直接 `javac`，MTR 官方 jar 当 classpath | 本模组只改造 `org.mtr.*`，MTR 的类名**不混淆**，所以不需要重映射，也不需要 refmap |
| 需要联网下载 MC / 映射 / 依赖 | 只要 JDK 17+ | 能在完全离线的机器上构建 |
| 代价 | 换 MTR 版本必须重跑注入点校验 | 用 `tools/check_targets.py` 补上 |

## 二、`build.py`

```bash
python build.py                                 # 自动找上级目录 / libs 里的 MTR jar
MTR_JAR=/path/to/mtr-fabric-4.0.4.jar python build.py
```

产物固定为 `build/libs/MTR4Advanced-1.0.2.jar`，**不会自动部署到任何 `mods/` 目录**
（读代码确认：脚本里只有 `zipfile` 打包那一步写文件，没有任何复制到游戏目录的逻辑）。
改完记得手动拷。

### 2.1 找 MTR jar

顺序：

1. 环境变量 `MTR_JAR`（存在且是文件就直接用）；
2. `上级目录/*[Mm][Tt][Rr]*4.0.4*.jar`
3. `libs/*[Mm][Tt][Rr]*4.0.4*.jar`
4. 兜底：`*[Mm][Tt][Rr]*.jar`（**会打一行警告**，提示注入点可能失效，建议用 `MTR_JAR` 显式指定）

命中多个时取 `sorted()` 的第一个 → 结果可复现，不会靠文件系统顺序。
`mixin-0.8.7.jar` 会被显式排除。

> 用 glob 字符类 `[Mm][Tt][Rr]` 而不是写死大写或小写：**Windows 的 glob 不区分大小写，Linux / macOS 区分**。
> MTR 官方 release 的文件名是小写（`mtr-fabric-4.0.4.jar`），但玩家手里常被改成别的大小写写法，
> 只写一套 pattern 会在另一个平台上直接找不到 jar。

### 2.2 自动生成 Minecraft stub

本模组**不直接引用任何 `net.minecraft.*` 类**，但 javac 为了解析 MTR 映射层的继承链
（例如把 MTR 控件当成 `class_339` 传给 `addChild`）需要看到少量 Minecraft 类。

脚本的做法是**迭代补齐**：

```
预置 net/minecraft/class_339.java（根类，所有 stub 都继承它）
        │
        ▼
javac 编译本模组 ──失败──▶ 正则抓 "class file for net.minecraft.X not found"
        │                        │
        │                        ▼
        │                 生成 空壳 X extends class_339，编译进 STUB_OUT
        ▼
      成功（最多 40 轮）
```

- 只处理 `net.minecraft.*` 缺失；**其它**编译错误直接原样报错退出（不会用 stub 掩盖真问题）；
- stub 只进 `build/stubs/`，**不进最终 jar**；
- 实测在本机需要 **3 轮、7 个 stub** 收敛。

### 2.3 关键编译参数

```bash
javac -nowarn --release 17 -proc:none -encoding UTF-8 \
      -J-Duser.language=en -J-Duser.country=US \
      -d build/classes -cp <MTR.jar>:<mixin.jar>:<stubs> <sources>
```

| 参数 | 作用 |
| --- | --- |
| `--release 17` | 目标 Java 17（服务端 17 / 21 都能跑） |
| `-proc:none` | 关掉注解处理器（不需要 Mixin AP） |
| `-encoding UTF-8` | 源码里有中文注释与中文 UI 字符串 |
| `-J-Duser.language=en` | **让 javac 的报错保持英文**，否则上面那个 `class file for ... not found` 正则在中文 locale 下匹配不到 |

### 2.4 打包

用 Python 标准库 `zipfile`（`ZIP_DEFLATED`）：

- `build/classes/**` → jar 根目录；
- `src/main/resources/**` → jar 根目录（`fabric.mod.json`、`mtr4-advanced.mixins.json`）。

> `os.sep == '\\'` 时 CPython 的 `ZipInfo.from_file` 会把反斜杠换成 `/`，
> 不会产出 `cn\nansai\...` 这种坏路径。

**jar 不是逐字节可复现的**：zip 条目带文件 mtime。要对比两次构建，请比内容而不是哈希。

### 2.5 构建后自检

```bash
python -c "import zipfile;print('\n'.join(zipfile.ZipFile('build/libs/MTR4Advanced-1.0.2.jar').namelist()))"
```

期望看到：`cn/nansai/mtrspeed/**` 的 class + `fabric.mod.json` + `mtr4-advanced.mixins.json`，
**不应出现任何 `net/minecraft/` 条目**。

### 2.6 实测基准（1.0.2）

| 项 | 实测值 |
| --- | --- |
| `python build.py` | 退出码 0，`compilation ok (round 3, 7~8 stub(s))` |
| `python tools/check_targets.py` | 退出码 0，`ALL OK (18 项检查)`，无 MISS、无 WARN |
| `javap` 定位 | PATH 上通常**没有** `javap` → 回退逻辑会去 `JAVA_HOME` / 常见 JDK 目录里找 |
| 单目标产物 | 13 个条目：11 个 class（8 个 mixin + `Config` + `SpeedLogic` + `SidingMaxSpeedAccess`）+ 2 个 json |
| 发布产物（Forge） | 14 个条目：11 个 class + `MANIFEST.MF` + `META-INF/mods.toml` + mixin 配置 |
| `net/minecraft/` 条目 | **0 个**（stub 没有进 jar） |
| 多目标矩阵 | `build_release.py` 一次跑完 10 个目标：**10/10 编译通过，注入点各 18/18** |
| 构建可复现性 | 同一目标两次构建的**条目 CRC32 逐一相同**；仅 zip 容器元数据不同（差 6 字节） |

> 也就是说：**class 内容可复现，jar 文件本身不逐字节可复现**（zip 条目带 mtime）。
> 想比对两次构建，比条目 CRC32 或解包后的内容，别比整包哈希。

> 待办（低优先级）：让 `build.py` 结尾自动调 `check_targets.py`，失败非零退出 ——
> 现在是两步手工，迟早会忘。见 [已知限制与路线图](已知限制与路线图.md)。

## 二·五、`build_release.py`（多版本发布矩阵）

```bash
python build_release.py --jars _mtr_jars --out ../releases      # 全部 10 个目标
python build_release.py --only 1.20.1:fabric                    # 只做一个
```

输入：`--jars` 目录下的 `MTR-<loader>-4.0.4+<MC>.jar`（从 MTR 官方渠道按版本下载）。
输出：**一个模组版本一个文件夹**：
`<输出目录>/1.0.2/MTR4Advanced-1.0.2-1.20.1Fabric.jar`（10 个 jar 都在这个版本文件夹里）。

**每个目标都会独立走一遍完整流程**（不复用其它目标的结果）：

| 步骤 | 说明 |
| --- | --- |
| 1. 生成平台元数据 | Fabric → `fabric.mod.json`；Forge → `META-INF/mods.toml` + MANIFEST 的 `MixinConfigs` |
| 2. 编译 | 对着**该目标自己的 MTR jar** 编译，并按需迭代补 `net.minecraft` stub |
| 3. 校验注入点 | 对着同一个 MTR jar 跑 `check_targets.py`，必须 18/18 |
| 4. 打包 | class + 元数据 + mixin 配置 |

**任一目标失败 → 整体退出码 1**，并在结尾列出未通过的目标。不会用「跳过失败项」糊弄过去。

### 平台差异（踩过的坑）

| | Fabric | Forge |
| --- | --- | --- |
| mixin 注册 | `fabric.mod.json` 的 `mixins` 数组 | **jar MANIFEST 的 `MixinConfigs` 属性**（Forge 靠它加载 mixin 配置，MTR 自己的 Forge 版就是这么做的） |
| mod id | `mtr4-advanced` | `mtr4advanced` —— **Forge 的 modId 只允许 `[a-z0-9_]`，连字符非法** |
| 依赖声明 | `depends` / `breaks` 用 Fabric 的版本谓词 | `mods.toml` 用 Maven 区间（`[1.20.1]`、`[4.0.4,4.0.5)`） |
| 映射层 | Minecraft 类型都藏在占位符 **`class_339`** 后面 | **直接用真实类名**（`net.minecraft.client.gui.components.AbstractWidget`、`net.minecraft.client.gui.GuiGraphics`） |

最后一行是本次最容易踩的坑：stub 生成器原本把所有 stub 都写成 `extends class_339`，
在 Fabric 上没事（因为整条链都是 `class_339`），到 Forge 就炸：

```
error: incompatible types: TextFieldWidgetExtension cannot be converted to AbstractWidget
        ((ScreenExtension) (Object) this).addChild(new ClickableWidget(mtr4a$textFieldMaxSpeed));
```

修法是给 stub 加层级规则：`net.minecraft.client.gui.*` 下的 stub 统一挂在
`net.minecraft.client.gui.components.AbstractWidget` 之下，其余仍挂在 `class_339` 之下。
（顺带把 `build.py` 里同一处逻辑也修了：stub 写在别的包时必须用全限定名 `net.minecraft.class_339`。）

## 三、`tools/check_targets.py`

不需要 Minecraft 运行时，纯靠 `javap` 静态比对，回答一个问题：

> **我注入的方法/调用点，在 MTR 4.0.4 里真的存在、而且唯一吗？**

### 3.1 它检查什么

1. **宿主方法存在**：从编译好的 mixin class 里用 `javap -p -v` 抓出注解里的 `method=...` 字符串，
   再 `javap -p` 读 MTR jar 里目标类，比对同名方法是否存在。
2. **被调用方法存在**：抓注解里的 `target=...`，拆出 owner / 方法名 / 描述符，比对 owner 类是否有这个方法。
3. **调用点在宿主方法内唯一**（本项目自己加的强化）：
   用 `javap -p -c` 反汇编宿主方法，**只在宿主方法体内**数目标方法的调用次数。
   `@Redirect` 没写 ordinal 时必须是 **1** —— 否则 MTR 改版新增调用点后会**静默命中错误位置**。

> 为什么必须限定在宿主方法里数：整个类里数会把别的方法也算进来
> （例如 `Siding#getUpcomingSlowerSpeed` 内部也调了 `PathData#getSpeedLimitMetersPerMillisecond`，
> 但那不是我们的注入点）。

### 3.2 用法

```bash
python tools/check_targets.py                      # 用默认 jar 路径
python tools/check_targets.py --jar /path/to/mtr-fabric-4.0.4.jar --classes build/classes
python tools/check_targets.py --javap /path/to/javap
```

> ⚠️ **脚本里的默认 jar 路径是写死的**，换一台机器就不成立。
> 必须用 `--jar` 显式指定，否则直接报「找不到 MTR jar」。
> 想一劳永逸：把默认值改成相对路径（如 `../*[Mm][Tt][Rr]*4.0.4*.jar`）或从 `MTR_JAR` 环境变量读。

### 3.3 预期输出

```
  OK    cn.nansai.mtr4advanced.mixin.SidingMixin -> org.mtr.core.data.Siding#updateData
  OK    cn.nansai.mtr4advanced.mixin.SidingSchemaMixin -> org.mtr.core.generated.data.SidingSchema#serializeData
  OK    cn.nansai.mtr4advanced.mixin.SidingTimeSegmentsMixin -> org.mtr.core.data.Siding#generatePathDistancesAndTimeSegments
  OK    cn.nansai.mtr4advanced.mixin.SidingTimeSegmentsMixin -> org.mtr.core.data.Siding#getUpcomingSlowerSpeed(...)
  OK    调用点 1 处（org.mtr.core.data.Siding#getUpcomingSlowerSpeed）
  ... （共 18 项）
ALL OK (18 项检查)
```

- 全部通过 → 退出码 0；
- 任何一项 `MISS` / 调用点不是 1 → 退出码 1，并提示
  「Mixin 运行时可能抛 InvalidInjectionException 或静默命中错误位置」。

`MISS` 意味着运行时**一定会**报 `InvalidInjectionException`；调用点 `WARN` 更危险，
它可能什么错都不报，只是限速悄悄算错。

### 3.4 找 javap 的顺序

PATH 上常常只有 Oracle 的 `javapath`（只有 `java` / `javac`，**没有 `javap`**），
`JAVA_HOME` 也未必设置。所以：

```
显式 --javap 参数  >  PATH  >  JAVA_HOME  >  常见 JDK 安装目录（按真实版本号降序）
```

> **按真实版本号**而不是字符串反序：`jdk1.8.0_202` 字符串序会排在 `jdk-21` 前面，
> 而 **javap 8 读不了 release 17 的 class —— 它会静默返回空结果**，
> 于是 18 项检查变成 0 项，脚本还会告诉你「ALL OK」。这个坑已经修掉了。

### 3.5 Windows 控制台编码

脚本输出含中文。在 Windows 上把输出重定向到文件时，如果控制台代码页不是 UTF-8，
日志里会出现乱码（历史上 `build/check_targets.log` 就是这么来的）：

```powershell
$OutputEncoding = [Console]::OutputEncoding = [Text.Encoding]::UTF8
$env:PYTHONIOENCODING = "utf-8"
python tools/check_targets.py | Tee-Object build/check_targets.log
```

乱码只影响日志可读性，**不影响检查结果与退出码**。

## 四、换 MTR 版本时怎么做

1. 拿到新版 MTR jar，`MTR_JAR=<新 jar> python build.py` —— 先看编译是否还过。
2. `python tools/check_targets.py --jar <新 jar>`：
   - 出现 `MISS` → 宿主方法/被调用方法被改名或移除 → 必须先改注入点；
   - 出现调用点 `WARN`（≠1）→ 必须给 `@Redirect` 补 `ordinal`，或重写注入方式；
   - 全 OK 也只是「注入点还在」，**语义是否变了**仍需人工比对（例如目标速度的计算顺序）。
3. 若新版 MTR 改了 `simulateMoving` 的控制流（比如手动分支的位置变了），
   要重新确认 [工作原理](工作原理.md#15-控制流手动分支在-ato-之前) 里的假设。
4. 新增 / 删除 mixin 类时，记得同步维护 `check_targets.py` 里的 `MIXIN_TARGETS` 字典 ——
   **字典里没有的类会被静默跳过，等于没校验**。

## 五、常见输出与排错

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `找不到 MTR jar，请设置环境变量 MTR_JAR` | 自动查找失败 | `MTR_JAR=/path/to/mtr-fabric-4.0.4.jar python build.py` |
| `警告：没找到 MTR 4.0.4，回退到 ...` | 只有别的版本 | 换回 4.0.4，或确认新版注入点仍然有效 |
| `缺少 .../libs/mixin-0.8.7.jar` | 缺第三方库 | 从仓库取 `libs/mixin-0.8.7.jar` |
| `stub generation exceeded limit` | 40 轮还没收敛（通常不是 stub 问题） | 看完整 javac 输出，多半是源码真的有别的编译错误 |
| `找不到 MTR jar: <默认路径>`（check_targets） | 用了写死的默认路径 | 加 `--jar` |
| `FileNotFoundError: javap` | PATH 没有 javap 且没找到 JDK | 装 JDK 或用 `--javap` 指定 |
| `找不到编译输出目录（先跑 build.py）` | 没编译过 | 先 `python build.py` |
