# 已知限制与路线图

这一页把「**故意不做**的」「**记录在案还没做**的」「**行为边界**的」三件事分清 ——
避免把设计取舍当成 bug 反复排查。

---

## 一、明确决策：不做

### 1. 手动驾驶完全不生效

**现状**：手动驾驶（`manual`）模式下，车尾控制提速 / 列车最高时速 / 跟随晚点浮动**三项全部不参与**。

**原因**（`Vehicle#simulateMoving` 的控制流）：

```
isClientside 分支 → 制动距离计算 → isCurrentlyManual() 分支 → ATO 自动路径
                                      ↑ 排在 ATO 之前，结尾 goto 跳过 ATO
```

本模组重定向的两个取值点（`Siding#getUpcomingSlowerSpeed`、`PathData#getSpeedLimitMetersPerMillisecond`）
都在被跳过的 ATO 路径里。手动时目标速度走 `VehicleExtraData#getMaxManualSpeed()`。

**为什么不改**：手动是给人开的，硬夹目标速度手感会很怪；做 ATP（超速才强制制动）则超出当前范围。
—— 这是明确记录在案的取舍，不是漏了。

**如果你想要**：在手动分支里另加注入点。两种语义：

- **ATP 语义**：只在超过 cap 时施加制动（推荐，手感影响最小）；
- **硬夹语义**：直接把目标速度夹到 `min(限速, cap)`（手感会明显变沉）。

### 2. 输入框无法输入小数

输入框的正则过滤器只放行数字，且 `maxLength = 4` → 只能填 `0`~`9999` 的整数。
代码里保留了小数显示（`mtrspeed$format`，最多 3 位）与格式化分支，但**界面改不出来**。
不影响 99% 的整数用法（列车限速本来就是 80 / 100 / 120 这种）。

### 3. 界面无溢出保护

四行控件是固定行高、无滚动条。GUI scale 调大或窗口很矮时，第 3 / 4 行会画出屏幕外。
见 [侧线界面](侧线界面.md#二布局是相对的不是写死坐标)。

## 二、记录在案，尚未处理

| # | 项 | 影响 | 备注 |

| 4 | **配置无热重载** | 面板服改一个布尔要重启整个服务端 | 低成本可做：加个定时 mtime 检查或指令重载 |
| 5 | **`breaks` 拦不住 4.1.x** | `>=4.0.5 <4.0.6` 只挡住 4.0.5；4.0.6+ / 4.1.x 会被放行，然后在运行时注入失败 | 每加一个被验证过的版本就要维护区间 |

| 7 | **每 tick 两次二分 + 扫描** | 超长线路 + 大量列车时有累计开销（`O(log n + k)`） | 没实测到问题；真要优化可缓存占用区间 |
| 8 | **`BATCH_SIZE = 40` 是拍脑袋值** | 大车场可能仍需多包；极端长线路侧线仍可能超单包上限 | 没有实测依据，等有人踩到再调 |
| 9 | **`check_targets.py` 不校验 `@Accessor` 字段名** | 改 MTR 版本时，访问器字段改名不会被脚本拦住 | 需给脚本加一类 `value=` 注解解析 |
| 10 | **`check_targets.py` 默认 jar 是作者本机绝对路径** | 别人拿到仓库必须加 `--jar` | 上架前建议改成相对路径 / 环境变量 |
| 11 | **`fabric.mod.json` 没有 `icon`** | 模组列表里没有图标 | 可选 |

## 三、行为边界（不是缺陷，是设计）

| 边界 | 说明 |
| --- | --- |
| 时刻表**不回溯** | 侧线改完车型 / 最高时速后，已生成的计划时间不会自动重算；要等列车重新生成路径或重启存档 |
| 只按**当前**车型长度算 | 中途换车型不会修正历史计划时间 |
| 只针对 **MTR 4.0.4** 校验 | 换版本必须重跑 `check_targets.py`，且语义变化仍需人工确认 |
| 侧线字段是**扩展 key** | 没装本模组的服务端会跳过它们（不清零、不报错）—— 这是有意选的兼容策略 |
| 上限默认是**天花板**不是目标 | 硬顶模式下 \`min(线路限速 × 晚点增益, 上限)\`，线路限速低时按线路限速跑 |
| 「复制到车场」是**单向、无回执** | 文案刻意写「已提交」，非 OP 时服务端会丢包 |

## 四、路线图

按「性价比」排序的候选改进，源自 `CODE_REVIEW.md` 第四轮的「还能加些什么」。

### 优先做

| 顺序 | 项 | 为什么 |
| --- | --- | --- |
| 1 | **调试 HUD**（F3 风格叠加层，实时显示 `target / railLimit / occupiedMin / cap / deviation / powerLevel`） | 做后面任何一项之前先做它，开发效率差 3 倍 |
| 2 | **惰行（coasting）**：`powerLevel` 插入 0 档 | 观感提升最直接；MTR 只有 ±5（全加速/全制动），接近降速点或停车点时先滑行更现实 |
| 3 | **起停附加时分** | 现在时刻表只按巡航速度积分，加上「启动附加 + 停车附加」才更接近实跑 —— 结构性晚点的最后一公里 |
| 4 | **晚点归因日志** | 持续晚点超阈值时打一行原因（前车占用 / 本侧线 cap / 时刻表不准），解决「到底是我这个模组还是 MTR 幽灵停车」的扯皮 |

### 值得做

| 项 | 价值 |
| --- | --- |
| 牵引力随速度衰减 `accel(v) = a0 · (1 - v/vmax)` | 电车真实特性（现在全速度区段恒定加速度） |
| Siding UI 直接显示推算出的总运行时分 | 调 cap 时手感差别很大 |
| 配置热重载 | 见上表第 4 项 |
| `build.py` 结尾自动跑 `check_targets.py` | 现在是两步手工，迟早会忘 |
| 版本号单一来源（`build.py` 读 `fabric.mod.json` 的 version） | 目前 `fabric.mod.json` / jar 名 / README 三处手工同步 |

### 再远一点

曲线/道岔自动限速（从相邻 `PathData` 的起终点向量算转角）、坡度影响（地铁基本平坡，收益低）、
时刻表 ↔ 实跑偏差对比表、Depot 列表加一列「最高时速」、车型预设下拉（80/100/120/160/350）、
「复制」支持跨车场 / 按线路筛选 / 撤销。

### 已排除

- **手动驾驶 ATP**：见第一节，属于明确取舍（想做的话 ATP 语义 > 硬夹语义）。

## 五、决策记录

| 决策 | 结论 | 理由 |
| --- | --- | --- |
| 硬顶公式与文档不符（P1-2） | **保留实现，改文档** | 晚点追赶是 MTR 原版机制，本模组只想加一个不受增益放大的天花板，不想顺手改掉原版行为 |
| 「降速由车头控制」的措辞（P2-1） | **改文档**：`tail-controlled-acceleration` 实际同时作用于加速与制动 | 让文档写实，并给出「彻底只看车头」的改法 |
| 手动驾驶不生效（P1-1） | **不改，缩小承诺** | 见第一节 |
| 「复制到车场」是假成功（P1-2 第四轮） | **改文案 + 文档** | 客户端拿不到回执是 MTR 的协议结构决定的，改不掉；如实告知生效前提 |
