# 配置参考

配置文件只有一个：**`config/mtr4-advanced.properties`**，四个键，没有 GUI 界面。

> **服务端的那一份才是权威。** 限速计算（`Vehicle#simulateMoving`）和时刻表推算
> （`Siding#generatePathDistancesAndTimeSegments`）都只在服务端跑；客户端那份基本不参与行车计算。

---

## 一、文件到底落在哪

```
FabricLoader.getInstance().getConfigDir()   ← 优先（通过反射调用，编译期不依赖 fabric-loader）
        │ 取不到
        ▼
System.getProperty("user.dir") + "/config"  ← 兜底
```

优先用 Fabric 认的游戏目录，**不是**写死 `user.dir`。原因：

> 双击 jar / 从别的目录跑启动脚本 / 面板服（Pterodactyl 等）/ systemd 起服务端时，
> 进程的工作目录（`user.dir`）**往往不是游戏目录** → 配置被写到别处，
> 服务端静默跑默认值。表现是「配置明明改了却没生效」，而且日志里什么都不报 —— 最难查的那类 bug。

**首次启动**会在日志里打一行，这是排查配置问题的第一现场：

```
[MTR4 Advanced] 已生成默认配置: <游戏目录的绝对路径>/config/mtr4-advanced.properties
```

> 找不到配置文件 / 改了没生效 → **先看这行**，用打印出来的绝对路径去找文件。

## 二、加载时机

- **懒加载 + 记忆化**：第一次真正需要配置时才读盘（`Config.load()`），读一次之后就不再读了。
- **双检锁 + `volatile`**：客户端渲染线程和服务端线程都可能触发加载，
  `loaded = true` 放在四个字段**全部赋值之后**，配合 `volatile` 的 happens-before 保证可见性。
  （首轮审查的 P0：之前 `loaded` 置位太早且无内存屏障，会让服务端永久跑在默认配置上。）
- **没有热重载**：改完必须重启游戏 / 服务端。这是已知限制，见 [已知限制与路线图](已知限制与路线图.md#二记录在案尚未处理) 第 4 项。
- **读失败怎么办**：`Properties.load` 抛异常时打一行 `[MTR4 Advanced] 读取 ... 失败，使用默认配置` 到
  `System.err`（会被收进 `latest.log`），然后**用默认值继续跑**，且 `loaded` 依然置位 —— 也就是**不会重试**。
- 文件不存在时会**手写一份带中文注释的默认配置**（UTF-8 写；读取端 `Properties.load(InputStream)` 是 ISO-8859-1，
  但 `#` 开头的注释行整个被跳过，不影响解析）。

## 三、四个键

```properties
tail-controlled-acceleration=true
default-max-speed-kmh=0.0
apply-max-speed-to-time-segments=true
apply-vehicle-length-to-time-segments=true
```

### 1. `tail-controlled-acceleration`

| 项 | 值 |
| --- | --- |
| 类型 | 布尔 |
| 默认 | `true` |
| 作用范围 | **加速目标**与**制动目标** |

- `true`：加速目标取「列车占用区间 `[车尾, 车头]` 内的最低线路限速」—— 车尾没通过提速点就不许加速（现实逻辑）。
  同时，制动目标也会与占用区间最低限速再取一次 `min`。
- `false`：完全回到 MTR 原版行为（车头一进高速段就加速）。

> **注意 `true` 同时管加速和制动。** 严格说这让车尾也参与了降速控制，与「降速由车头控制」的概括略有出入；
> 实际影响很小（车尾里程必然在车头之后，压出来的值通常 ≤ 已经在跑的速度），
> 但极端工况（车尾尚在低速区 + 前方又出现更低限速）会叠加出偏早的制动。
> 想彻底回到「降速只看车头」，删掉 `SpeedLogic#getDecelerationTarget` 里那个 `if` 即可。

### 2. `default-max-speed-kmh`

| 项 | 值 |
| --- | --- |
| 类型 | 浮点数（km/h） |
| 默认 | `0.0`（不限制） |
| 作用范围 | 运行时 + 时刻表推算 |

侧线里没填「列车最高时速」时用的默认值。`≤ 0` 一律视为不限制（返回 `Double.MAX_VALUE`，后续 `min` 自然失效）。

适用场景：整个服务器统一限速（例如全服车型最高 100），不想一条条侧线去填。

### 3. `apply-max-speed-to-time-segments`

| 项 | 值 |
| --- | --- |
| 类型 | 布尔 |
| 默认 | `true` |
| 作用范围 | **仅**时刻表推算 |

把「列车最高时速」套进侧线的时刻表推算。关掉的话：线路限速 120、列车限速 80 时，
时刻表按 120 算 → 列车**永远显示晚点**。默认开。

### 4. `apply-vehicle-length-to-time-segments`

| 项 | 值 |
| --- | --- |
| 类型 | 布尔 |
| 默认 | `true` |
| 作用范围 | **仅**时刻表推算 |

时刻表按**发车侧线自己的列车长度**，取 `[车尾, 车头]` 区间内的最低限速。

这是「结构性晚点」的根因修复：运行时是车尾控制提速，而 MTR 原版时刻表是**质点模型**
（只看车头那一点），两者不一致 → 计划时间永远比实际跑得短 → 晚点只累积不消掉。
打开后不同车型（不同编组长度）的侧线各算各的，互不干扰。

## 四、解析规则的坑

实现用的是最朴素的 `Boolean.parseBoolean` 与 `Double.parseDouble`，**失败即静默回退默认值**：

| 你写的 | 实际解析结果 |
| --- | --- |
| `tail-controlled-acceleration=true` / `TRUE` / `True` | `true` |
| `tail-controlled-acceleration=1` / `yes` / `on` | **`false`** —— `Boolean.parseBoolean` 只认 `true`（忽略大小写），其它一律 false |
| `default-max-speed-kmh=80` | `80.0` |
| `default-max-speed-kmh=80 km/h` | 解析失败 → **回退 `0.0`（不限制）**，只在启动时打一次失败日志 |
| `default-max-speed-kmh=-1` | 视为**不限制**（`> 0` 判断） |
| 键名拼错 / 少写一个键 | 该键用默认值，不报错 |

配置文件里未出现的键**不会**被写成默认值 —— 只有整个文件不存在时才会生成一份完整的默认文件。
少了某个键时用的是代码里的默认常量，和默认文件里的值一致。

## 五、怎么确认配置真的被读到了

1. 日志里搜 `[MTR4 Advanced]`：
   - `已生成默认配置: <路径>` → 文件不存在，本次用的是默认值；
   - `读取 <路径> 失败，使用默认配置` → 文件存在但读挂了（权限 / 编码 / 损坏）。
2. 用打印出来的**绝对路径**确认文件就在你以为的地方。
3. 行为验证（最直接）：
   - `tail-controlled-acceleration=false` → 车头一进高速段整列车立刻加速（回到原版手感）；
   - `default-max-speed-kmh=60` 且侧线填空 → 列车封顶 60 km/h（硬顶模式下连晚点追赶也破不了 60）。

## 六、服务端部署注意（面板服 / systemd）

- 模组 `environment: "*"`，但界面相关的两条 Mixin（`client.SidingScreenMixin`、
  `access.SavedRailScreenBaseAccess`）放在 mixin 配置的 `"client"` 数组里，
  **专用服务端不会加载它们** → 服务端不需要任何 Minecraft 客户端类，不会 `NoClassDefFoundError`。
- Java 版本：编译用 `--release 17`，运行 Java 17 / 21 均可。
- 调参请改**服务端**的配置文件。只改客户端那份，对行车没有任何影响。
