# 工作原理

这一页解释三个特性的完整推导：**为什么这么改**、**改在哪个字节码位置**、**公式怎么来的**。
只想知道怎么用，看 [侧线界面](侧线界面.md) 和 [配置参考](配置参考.md) 就够了。

---

## 一、MTR 4.0.4 的原始行为

### 1.1 加速目标：只看车头所在的那一个轨段

`Vehicle#simulateMoving` 里，ATO 路径算出目标速度大致是这样：

```java
speedTarget = pathData[currentIndex].getSpeedLimitMetersPerMillisecond() * deviationSpeedAdjustment;
```

`currentIndex` 是**车头**所在的轨段。也就是说：

> 车头一进入 120 km/h 区段，整列车立刻开始加速 —— 哪怕车尾还压在 40 km/h 的道岔上。

### 1.2 制动目标：基于车头的前瞻制动曲线

`Siding#getUpcomingSlowerSpeed(path, currentIndex, railProgress, currentSpeed, deceleration)`
从车头位置往前看，找出「以当前减速度能在到达前降到」的那个更低限速。
**返回值 < 0 表示前方没有更低限速**（原版语义，本模组原样保留）。

### 1.3 晚点追赶：在取完限速之后乘一个增益

MTR 支持「晚点追赶」：列车晚点时把目标速度乘上 `deviationSpeedAdjustment`（无晚点时恒为 `1.0`，
最多默认 `1.25`）。字节码里 `simulateMoving` 的制动路径（bc 434-441）与 ATO 路径（bc 465-473）
各有一处 `dmul`。

**关键点：增益是最后一步乘上去的。** 任何想在「最终速度」上做的上限，都必须考虑这个乘法 —— 见第三节。

### 1.4 时刻表：质点模型

`Siding#generatePathDistancesAndTimeSegments` 按车头那一点的限速积分出计划时间。
运行时的行为（1.1 改完之后的整列通过）与它不一致 → **计划时间永远比实际跑得短** → 结构性晚点。

### 1.5 控制流：手动分支在 ATO 之前

```
simulateMoving
├── isClientside 分支
├── 制动距离计算
├── isCurrentlyManual() 分支 ──┐  目标速度 = VehicleExtraData#getMaxManualSpeed()
│                              │  结尾 goto 直接跳过下面整段
└── ATO 自动路径  ◀────────────┘  ★ 本模组的两个注入点都在这里面
```

所以**手动驾驶模式下三项功能全部不参与**。这是已知取舍，理由见
[已知限制与路线图](已知限制与路线图.md#1-手动驾驶完全不生效)。

## 二、占用区间：本模组唯一新增的坐标概念

MTR 内部本来就用这个区间描述「列车占了哪一段路」（见 `Vehicle#writeVehiclePositions`）：

```
车头 = railProgress
车尾 = railProgress - 列车总长
占用区间 = [railProgress - 列车总长, railProgress]
```

- `railProgress` 是沿路径的**里程**（米），**不是**百分比、不是下标。
- 反向行驶（`reversed`）也一样成立 —— 车头永远在里程较大的那一端，所以**不需要区分行驶方向**。
- 时刻表推算里的初值 `(railLength + 车长) / 2` 就是「列车居中停在侧线上时的车头位置」；
  运行时 `Vehicle#simulateInDepot` 也是 `railProgress = vehicleExtraData.getDefaultPosition()`。
  **两侧口径一致**，这是「时刻表能对上实跑」的前提。

「占用区间内的最低线路限速」由 `SpeedLogic#occupiedMinimumSpeedLimit` 算：

```java
int startIndex = indexOfStartDistance(path, tail);   // 二分：最后一个 startDistance <= tail
int endIndex   = indexOfStartDistance(path, head);
if (endIndex < 0)   return fallback;
if (startIndex < 0) startIndex = 0;                  // 车尾还没入路径
double result = Double.MAX_VALUE;
for (int i = startIndex; i <= endIndex && i < path.size(); i++) {
    PathData pathData = path.get(i);
    if (pathData.getEndDistance()   < tail) continue;
    if (pathData.getStartDistance() > head) break;
    result = Math.min(result, pathData.getSpeedLimitMetersPerMillisecond());
}
return result == Double.MAX_VALUE ? fallback : result;
```

复杂度 `O(log n + k)`（二分 + 区间内轨段线性扫描），每 tick 调用两次。

## 三、限速公式

### 3.1 两个注入点

```java
@Mixin(Vehicle.class)
public class VehicleSpeedMixin {

    @Redirect(method = "simulateMoving",
              at = @At(value = "INVOKE",
                       target = "Lorg/mtr/core/data/PathData;getSpeedLimitMetersPerMillisecond()D"))
    private double mtr4a$railSpeedLimit(PathData pathData) {
        return SpeedLogic.getAccelerationTarget((Vehicle) (Object) this,
                                               pathData.getSpeedLimitMetersPerMillisecond());
    }

    @Redirect(method = "simulateMoving",
              at = @At(value = "INVOKE",
                       target = "Lorg/mtr/core/data/Siding;getUpcomingSlowerSpeed(...)D"))
    private double mtr4a$upcomingSlowerSpeed(ObjectList<PathData> path, int currentIndex,
                                                double railProgress, double currentSpeed,
                                                double deceleration) {
        final double original = Siding.getUpcomingSlowerSpeed(path, currentIndex, railProgress,
                                                             currentSpeed, deceleration);
        return SpeedLogic.getDecelerationTarget((Vehicle) (Object) this, original);
    }
}
```

> `@Redirect` **没有写 ordinal**，这依赖「宿主方法里每个目标调用点恰好 1 处」。
> `tools/check_targets.py` 会专门校验这一点（见 [构建与工具](构建与工具.md)）——
> MTR 改版后新增了调用点却没人发现，会**静默命中错误位置**。

### 3.2 加速目标

```java
public static double getAccelerationTarget(Vehicle vehicle, double rawLimit) {
    Config.load();
    double limit = rawLimit;
    if (Config.tailControlledAcceleration) {
        limit = Math.min(limit, getOccupiedMinimumSpeedLimit(vehicle, limit));
    }
    return applyHardCap(vehicle, limit);
}
```

- `rawLimit` = 原版车头所在轨段的限速；
- 开启车尾控制时，与占用区间最低限速取 `min` → **车尾没通过提速点就不许加速**；
- 最后套列车最高时速。

### 3.3 制动目标

```java
public static double getDecelerationTarget(Vehicle vehicle, double upcomingSlowerSpeed) {
    Config.load();
    if (upcomingSlowerSpeed < 0) {
        return upcomingSlowerSpeed;                  // 前方没有更低限速，保持原版语义
    }
    if (Config.tailControlledAcceleration) {
        upcomingSlowerSpeed = Math.min(upcomingSlowerSpeed,
                                       getOccupiedMinimumSpeedLimit(vehicle, upcomingSlowerSpeed));
    }
    return applyHardCap(vehicle, upcomingSlowerSpeed);
}
```

制动曲线本身仍然是**基于车头的**（原版 `getUpcomingSlowerSpeed` 未改动）；
`tail-controlled-acceleration = true` 时额外与占用区间最低限速取一次 `min`。

### 3.4 硬顶：为什么是「先除后乘」

上游拿到目标速度后还会乘一次 `A = deviationSpeedAdjustment`。所以：

```java
private static double applyHardCap(Vehicle vehicle, double limit) {
    final double cap = getTrainMaxSpeedMetersPerMillisecond(vehicle);
    if (cap == Double.MAX_VALUE) return limit;            // 没设上限
    if (shouldFollowDeviation(vehicle)) {
        return Math.min(limit, cap);                      // 浮动模式
    }
    final double adjustment = ((VehicleAccess) vehicle).mtr4a$getDeviationSpeedAdjustment();
    final double safeAdjustment = adjustment > 0 ? adjustment : 1.0;
    return Math.min(limit, cap / safeAdjustment);         // 硬顶模式
}
```

| 模式 | 本函数返回 | 上游再 `× A` | 最终目标速度 |
| --- | --- | --- | --- |
| 硬顶（不勾） | `min(limit, cap / A)` | `× A` | **`min(limit × A, cap)`** |
| 浮动（勾选） | `min(limit, cap)` | `× A` | **`min(limit, cap) × A`** |

`cap` 的来源优先级（`getTrainMaxSpeedMetersPerMillisecond`）：

```
侧线的「列车最高时速」  >0  →  用它
                      ≤0  →  Config.default-max-speed-kmh  >0  →  用它
                                                              ≤0  →  Double.MAX_VALUE（不限制）
```

单位换算是 `km/h ÷ 3600 = m/ms`，与 MTR 内部 `Utilities` 的换算一致。

## 四、时刻表推算怎么对齐运行时

`SidingTimeSegmentsMixin` 在 `Siding#generatePathDistancesAndTimeSegments` 上挂两个 `@Redirect`，
解决「运行时按整列通过、时刻表按质点」的不一致。

### 4.1 先借一次调用抓上下文

局部变量（`path`、`railProgress`、`totalVehicleLength`）在 handler 里拿不到，
只能从方法签名里能拿到的那个调用点借：

```java
@Redirect(method = "generatePathDistancesAndTimeSegments",
          at = @At(value = "INVOKE",
                   target = "Lorg/mtr/core/data/Siding;getUpcomingSlowerSpeed(...)D"))
private double mtr4a$captureAndCapUpcomingSlowerSpeed(ObjectList<PathData> path, int currentIndex,
        double railProgress, double currentSpeed, double deceleration) {
    mtr4a$capturedPath = path;
    mtr4a$capturedRailProgress = railProgress;
    mtr4a$capturedVehicleLength = Siding.getTotalVehicleLength(
            ((Siding) (Object) this).getVehicleCars());
    final double original = Siding.getUpcomingSlowerSpeed(path, currentIndex, railProgress,
                                                          currentSpeed, deceleration);
    return original < 0 ? original : Math.min(original, mtr4a$maxSpeedMetersPerMillisecond());
}
```

**为什么这样是安全的**（字节码证据）：`getSpeedLimitMetersPerMillisecond` 的调用点在同一次循环的后面
（bc 777 → 819），且到达 819 的唯一路径必经 777 —— 所以每次使用前上下文都必然刷新过，
不存在「跳过捕获直接用上一轮的旧值」。

`mtr4a$capturedVehicleLength` 每次刷新而**不做进程级缓存**：重算路径时车型可能变。
也不能在每个轨段的回调里现算 —— 原版在方法开头只算一次车长，逐轨段重算纯属浪费。

### 4.2 再压轨段限速

```java
@Redirect(method = "generatePathDistancesAndTimeSegments",
          at = @At(value = "INVOKE",
                   target = "Lorg/mtr/core/data/PathData;getSpeedLimitMetersPerMillisecond()D"))
private double mtr4a$capRailSpeedLimit(PathData pathData) {
    Config.load();
    double limit = pathData.getSpeedLimitMetersPerMillisecond();

    if (Config.applyVehicleLengthToTimeSegments && mtr4a$capturedPath != null
            && !Double.isNaN(mtr4a$capturedRailProgress)) {
        final double vehicleLength = mtr4a$capturedVehicleLength;
        if (vehicleLength > 0) {
            final double head = mtr4a$capturedRailProgress;
            limit = Math.min(limit, SpeedLogic.occupiedMinimumSpeedLimit(
                    mtr4a$capturedPath, head - vehicleLength, head, limit));
        }
    }
    return Math.min(limit, mtr4a$maxSpeedMetersPerMillisecond());
}
```

于是时刻表的目标速度 = `min(占用区间最低限速, 列车最高时速)`，**永远按硬顶算**
（推算时没有「晚点」这个概念，所以不受「跟随晚点浮动」影响）。

**不同车型的侧线各算各的**：车长取自 `Siding#getVehicleCars()` → `Siding.getTotalVehicleLength(...)`，
所以 4 节编组和 8 节编组的侧线，时刻表不一样。


### 序列化为什么拆成两个 Mixin

| 方向 | 注入点 | 原因 |
| --- | --- | --- |
| 读 | `Siding#updateData` TAIL | `updateData` 是 `Siding` 自己声明的方法 |
| 写 | `SidingSchema#serializeData` TAIL | `serializeData` 真正声明在父类 `SidingSchema` 上，Mixin **不会**为目标类凭空生成父类方法的 override |

写出时用 `instanceof Siding` 过滤 —— `Siding extends SidingSchema`，非 Siding 的实例不会被写入这两个字段。
`Siding#serializeFullData` 会经由 `SerializedDataBase` 的默认实现转调 `serializeData`，
所以**存档（full）和网络同步两条路都被覆盖到**。

## 六、边界与防御

代码里显式处理过的退化情况（都是审查中逐条确认过的）：

| 情况 | 行为 |
| --- | --- |
| `vehicle.vehicleExtraData == null` | 返回 `fallback`（原版取值），不猜 |
| `immutablePath` 为 null / 空 | 返回 `fallback` |
| 车头里程超出路径（`endIndex < 0`） | 返回 `fallback` |
| 区间内没扫到任何轨段 | 返回 `fallback` |
| 车尾还没入路径（`tail < 0` → `startIndex < 0`） | 回落到 `startIndex = 0`，不越界 |
| 写侧线字段时传 `NaN` / `Infinity` | 直接**忽略这次写入**（`Math.max(0, NaN)` 会返回 NaN，必须显式挡） |
| 写侧线字段时传负数 | 夹到 `0`（= 不限制） |
| `deviationSpeedAdjustment ≤ 0` | 按 `1.0` 兜底（实测原版恒 ≥ 1.0，这层是保险） |
| 反序列化时 key 缺失 | `ReaderBase.unpackValue` 反汇编为 `if (value == null) return;` → **callback 不被调用**，已有值不会被清零（单端安装 / 卸载安全） |

## 七、为什么不需要 refmap / 不重映射

Mixin 只改造 `org.mtr.*` 的类，而这些类名在 MTR 里是**稳定**的（不走 Minecraft 混淆重映射），
所以不需要 Mixin 注解处理器生成的 refmap，整个构建链路也就不需要 Gradle / Loom / 联网。
代价是：**换 MTR 版本必须重新校验注入点**。
